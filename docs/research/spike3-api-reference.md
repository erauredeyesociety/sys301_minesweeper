## 2. `motor` — one motor on one port

### 2.1 The surface, measured

```
dir(motor) -> stop  run  run_for_degrees  run_for_time  run_to_absolute_position
              run_to_relative_position  set_duty_cycle  get_duty_cycle  velocity
              absolute_position  relative_position  reset_relative_position
              status  info
constants  -> BRAKE  CANCELLED  CLOCKWISE  COAST  CONTINUE  COUNTERCLOCKWISE
              DISCONNECTED  ERROR  HOLD  LONGEST_PATH  READY  RUNNING
              SHORTEST_PATH  SMART_BRAKE  SMART_COAST  STALLED
```
`[MEASURED]`

Two things that had been open questions are now closed by that one line:

- **`motor.status()` and `motor.info()` exist on our firmware.** Both are undocumented by LEGO and were
  attested by only one mirror. They are on our hub. `[MEASURED]`
- **The spelling is `CANCELLED`, two L's.** The mirrors contain both `CANCELLED` (constants block) and
  `CANCELED` (prose); `motor.CANCELED` would be an `AttributeError` on a rare branch. **Settled.**
  `[MEASURED]`

### 2.2 Signatures, units and ranges

Everything after `*` is **keyword-only**. `[MIRROR]` for the signatures; units as noted.

| Call | Units / ranges | Returns |
|---|---|---|
| `motor.run(port, velocity, *, acceleration=1000)` | `velocity` **deg/s** · `acceleration` **deg/s²**, 1–10000 | `None` (fire-and-forget) |
| `motor.run_for_degrees(port, degrees, velocity, *, stop=BRAKE, acceleration=1000, deceleration=1000)` | `degrees` = **motor output-shaft degrees** | Awaitable → status int |
| `motor.run_for_time(port, duration, velocity, *, stop=BRAKE, …)` | `duration` **milliseconds** | Awaitable → status int |
| `motor.run_to_absolute_position(port, position, velocity, *, direction=SHORTEST_PATH, stop=BRAKE, …)` | `position` degrees; values outside the bounded range **wrap** (200 ≡ −160) | Awaitable |
| `motor.run_to_relative_position(port, position, velocity, *, stop=BRAKE, …)` | degrees from the last `reset_relative_position` | Awaitable |
| `motor.stop(port, *, stop=BRAKE)` | — | `None` |
| `motor.set_duty_cycle(port, pwm)` | `pwm` **−10000…+10000** — raw duty, **NOT percent**. Full forward is 10000. Bypasses the velocity controller entirely (open loop). | `None` |
| `motor.get_duty_cycle(port)` | same scale | int |
| `motor.velocity(port)` | ⚠ **`[UNVERIFIED]` — see § 2.5** | int |
| `motor.absolute_position(port)` | degrees, **bounded/wrapping**, ≈ −179…180 (endpoints disputed) | int |
| `motor.relative_position(port)` | degrees, **cumulative and unbounded** (int32) | int |
| `motor.reset_relative_position(port, position)` | declares the current physical position to be `position` | `None` |
| `motor.status(port)` | one of `READY/RUNNING/STALLED/CANCELLED/ERROR/DISCONNECTED`. **`[MEASURED]` 2026-08-27: an UNOCCUPIED port returns `5`** — all six ports A–F, nothing plugged in. Which *named* constant equals 5 is still unread (see § 2.3) | int |
| `motor.info(port)` | `[MIRROR]`, undocumented by LEGO: `(device_id, max_speed)` | tuple |

`port` is a value from `hub.port` (`dir(hub.port) -> A B C D E F` `[MEASURED]`). LEGO's protocol enum
fixes A=0x00 … F=0x05 `[LEGO]`, but the *Python* objects' integer values are `[UNVERIFIED]` on our hub —
always pass `port.C`, never a literal.

### 2.3 Constant values

Names are `[MEASURED]`. The integers come from LEGO's published protocol enums `[LEGO]` and are
**`[UNVERIFIED]` on our hub** — one `print(motor.BRAKE, motor.STALLED)` settles them.

| Group | Values `[LEGO]` |
|---|---|
| Stop | `COAST=0` `BRAKE=1` `HOLD=2` `CONTINUE=3` `SMART_COAST=4` `SMART_BRAKE=5` |
| Direction | `CLOCKWISE=0` `COUNTERCLOCKWISE=1` `SHORTEST_PATH=2` `LONGEST_PATH=3` |
| Status | `READY=0` `RUNNING=1` `STALLED=2` `CANCELLED=3` `ERROR=4` `DISCONNECTED=5` — ⚠ the *only* datum we have from our own hub is that an **empty port returns 5**, which is consistent with this table but does **not** confirm it: 5 could be `DISCONNECTED` or `SMART_BRAKE`-style overlap in a different enum. `print(motor.READY, motor.STALLED, motor.DISCONNECTED)` settles the whole row and has **not been run** (KU-M15) |

Behaviour `[MIRROR]`: `COAST` freewheels · `BRAKE` brakes and keeps braking (passive, no position
servo) · `HOLD` actively servos to hold position · `CONTINUE` does not stop at all, it keeps the
current velocity until the next command · **`SMART_COAST` / `SMART_BRAKE` additionally carry the
accumulated positional error into the next command.** The SMART variants are the ones that matter for a
sweep: they stop error accumulating leg over leg.

**Use the names, never the integers.** Every integer here is second-hand, and our one measurement
(empty port → 5) is not enough to promote any of them.

### 2.4 Sign convention

Positive degrees / positive velocity = **clockwise viewed from the top of the motor** (looking at the
output face); negative = counter-clockwise. `[MIRROR]`

> **Correction.** A verifier showed this is **single-sourced**: the "(when viewed from the top)"
> wording appears exactly once, on `run_for_degrees`, in the jvolkening mirror only. The tuftsceeo
> mirror carries no directional prose at all. Earlier drafts claimed "both mirrors" — they do not.

This is per-motor, not per-robot. The API has no notion of "forward". On a differential drive the two
motors are physically mirrored, so **one side must have its sign inverted** for a positive command to
drive forward. That is a build fact to be measured, not an API fact —
[../../src/hub_motors.py](../../src/hub_motors.py) already carries it as an `UNVERIFIED` note beside the
port map, which is the right place for it.

### 2.5 ⚠ `motor.velocity()` — units genuinely in doubt

LEGO's help says **deg/s**. Three things cut against taking that at face value:

1. The jvolkening mirror appends: *"empirical testing suggests the unit of the returned value is not in
   deg/sec"*.
2. LEGO's own BLE telemetry defines the motor speed field as **`int8`, −100…100** — a *percentage*.
   `[LEGO]`, `messages.html#x0a-devicemotor`.
3. LEGO's 45603 tech spec calls the rotation sensor a *"speed sensor (measures percentage of maximum
   design speed)"*. `[LEGO]`

So the underlying LPF2 device unambiguously reports percent-of-max. The only open question is whether
the SPIKE 3 `motor` wrapper rescales it. **`[UNVERIFIED]` — do not build a velocity feedback loop on
this until it is measured.** If it is percent, the medium-motor conversion is ×11.1. It is a one-line
bench check: command a known velocity, read it back, compare.

### 2.6 Odometry: `relative_position`, not `absolute_position`

`relative_position` is **cumulative and unbounded** — it does not wrap at ±180. LEGO's protocol carries
it as int32, so wraparound is ~5.9 million wheel revolutions away `[LEGO]`. `absolute_position` **does**
wrap; the exact endpoints are disputed three ways (−179…180 `[MIRROR]` vs −180…179 `[LEGO]` protocol vs
"−/+180" `[LEGO]` spec sheet). Immaterial unless code compares against a literal boundary.

SPIKE 3 removed SPIKE 2's unit machinery: there is **no `set_motor_rotation`, no `unit=` parameter, no
`set_default_speed`**. Converting distance to degrees is the program's job:

```
degrees = 360 * distance / (pi * wheel_diameter)
```

which is exactly why our unmeasured wheel diameter is load-bearing
([speed-envelope.md](./speed-envelope.md)).

### 2.7 Motor hardware specs `[LEGO]`

All figures from LEGO's own one-page tech specs, at the supply voltage each sheet states.

| Motor | No-load | API ceiling (= no-load × 6) | Max-efficiency | Stall torque | Stall current |
|---|---|---|---|---|---|
| Small 45607 | 110 RPM ±15% | ±660 deg/s | 1.8 N·cm @ 85 RPM (510 deg/s) | 5 N·cm | 340 mA |
| **Medium 45603** | 185 RPM ±15% | **±1110 deg/s** | 3.5 N·cm @ 135 RPM (810 deg/s) | 18 N·cm | 800 mA |
| Large 45602 | 175 RPM ±15% | ±1050 deg/s | 8 N·cm @ 135 RPM (810 deg/s) | 25 N·cm | 1400 mA |

Medium 45603 detail: 5–9 V, data at 7.2 V; no-load current 110 mA ±15%; rotation sensor **360 counts
per revolution (1°/count), accuracy ≤ ±3°, update rate 100 Hz**; absolute position ±180°; LPF2
connector, 250 mm wire.

**Two engineering consequences.**

1. **The API ceiling is the ZERO-TORQUE speed.** It is unreachable under any load. Build the speed
   budget against the **max-efficiency** figure — 810 deg/s for a medium or large, 510 for a small —
   not against 1110.
2. **Medium is *faster* than large** (185 vs 175 RPM) but has **2.3× less usable torque** (8 ÷ 3.5) and
   1.4× less stall torque. Speed cannot tell them apart — 5.7% is inside the ±15% tolerance band.
   Torque is the honest discriminator.
   > **Correction.** An earlier draft said "3.6× less usable torque" in one sentence and "2.3× apart"
   > two sentences later. 8/3.5 = **2.29**. The 3.6× figure was arithmetic error; 2.3× is right.

### 2.8 Identifying our two motors read-only

Both owned motors are of **unknown type** ([CLAUDE.md](../../CLAUDE.md) hard facts). LEGO publishes the
device-type IDs, and `motor.info(port)` is on our hub `[MEASURED]`, so identification needs **no motion
and no floor space**:

| id | Device |
|---|---|
| 48 (0x30) | Medium Angular 45603 (Education, white) `[LEGO]` |
| 49 (0x31) | Large Angular 45602 (Education, white) `[LEGO]` |
| 65 (0x41) | Small Angular 45607 (SPIKE Essential) `[LEGO]` |
| 75 (0x4B) | Technic Medium Angular 88018 (retail Powered UP, grey) — community registry |
| 76 (0x4C) | Technic Large Angular 88017 (retail Powered UP, grey) — community registry |

⚠ **An `OSError` from `device.id(port)` is the EMPTY-PORT signal, not a fault.** `[MEASURED]` 2026-08-27:
with nothing connected, `device.id()` raised `OSError` and `motor.status()` returned `5` on **all six**
ports. Whoever runs this on the day sees that first and must not read it as a dead hub — it means *check
the plug*. Catch it and report "empty", as [../../src/hub_selfcheck.py](../../src/hub_selfcheck.py) does.

If the team bought retail rather than Education motors, expect 75/76; **an unrecognised id is not a
failure.** The medium pair really is the same mechanical part (45603 and 88018 are both BrickLink
`54696c01`, different colour). The large pair is **not**: 45602 is `54675c01`, 88017 is `54675c02`.
> **Correction.** An earlier draft claimed both pairs were part-identical. Only the medium pair is.

```python
# Read-only. No motion. Returns None -- never a guess -- when it cannot read.
import motor
DEVICE_IDS = {48: ("Medium Angular 45603", 1110), 49: ("Large Angular 45602", 1050),
              65: ("Small Angular 45607", 660),  75: ("Medium Angular 88018", 1110),
              76: ("Large Angular 88017", 1050)}

def identify(p):
    try:
        device_id, max_speed = motor.info(p)      # UNDOCUMENTED by LEGO; present on our hub
    except (AttributeError, OSError, TypeError, ValueError):
        return None
    known = DEVICE_IDS.get(device_id)
    return known if known else ("UNKNOWN id=%d" % device_id, max_speed)
```

Until this is run, **`hub_motors.DRIVE_MAX_DPS` stays at the pessimistic 660.**

### 2.9 What does NOT exist in SPIKE 3 `motor`

`was_stalled` · `was_interrupted` · `set_stall_detection` · `get_degrees_counted` · `start` ·
`start_at_power` · `set_default_speed`. All are SPIKE 2 `Motor` **object methods** on a class this hub
cannot construct. Confirmed absent from our own `dir(motor)` `[MEASURED]`.

Stall handling is exactly two things: the `STALLED` status returned when you **await** a `run_*` call,
and `motor.status(port)`. No callback, no threshold setter. And a caveat `[MIRROR]`: *"`motor.run` does
not set status to `RUNNING`; other `run_*` functions do"* — so a fire-and-forget continuous drive is
**invisible to `status()`**, and a sweep-leg stall must be inferred from successive
`relative_position()` reads going flat while a nonzero velocity is commanded.

## 3. `motor_pair` — the differential drive primitive

```
dir(motor_pair) -> pair  unpair  move  move_tank  move_for_degrees
                   move_tank_for_degrees  move_for_time  move_tank_for_time  stop
constants       -> PAIR_1  PAIR_2  PAIR_3
```
`[MEASURED]`

There are **no pair-specific stop constants** — pass `motor.BRAKE` etc. from the other module.

| Call | Notes |
|---|---|
| `motor_pair.pair(pair, left_motor, right_motor)` | argument order **defines** which motor is "left" |
| `motor_pair.unpair(pair)` | |
| `motor_pair.move(pair, steering, *, velocity=360, acceleration=1000)` | fire-and-forget, returns `None` |
| `motor_pair.move_for_degrees(pair, degrees, steering, *, velocity=360, stop=BRAKE, …)` | Awaitable |
| `motor_pair.move_for_time(pair, duration, steering, *, velocity=360, stop=BRAKE, …)` | Awaitable |
| `motor_pair.move_tank(pair, left_velocity, right_velocity, *, acceleration=1000)` | both velocities **required** |
| `motor_pair.move_tank_for_degrees(pair, degrees, left_velocity, right_velocity, *, …)` | Awaitable |
| `motor_pair.move_tank_for_time(pair, left_velocity, right_velocity, duration, *, …)` | Awaitable |
| `motor_pair.stop(pair, *, stop=BRAKE)` | |

Units are identical to `motor`: velocities **deg/s**, degrees = **motor output degrees**, duration
**ms**, acceleration/deceleration **deg/s²** 1–10000. `[MIRROR]`

Note `velocity=360` is the **default** for every non-tank move — a modest 60 RPM.

### ⚠ 3.1 The argument-order trap

```python
await motor_pair.move_for_time(motor_pair.PAIR_1, 3000, 0, velocity=300)
#                                                 ^^^^ ms  ^ steering       duration is 2nd

await motor_pair.move_tank_for_time(motor_pair.PAIR_1, 0, 1000, 3000)
#                                             left_dps ^  ^^^^ right_dps  ^^^^ ms
#                                                                          duration is 4th

await motor_pair.move_for_degrees(motor_pair.PAIR_1, 720, 0, velocity=300)
await motor_pair.move_tank_for_degrees(motor_pair.PAIR_1, 720, 300, 300)
#                                                        ^^^ degrees is 2nd in BOTH
```

LEGO's own comment for that second line is *"Turn right for 3 seconds"*. All arguments are positional
ints, so a mix-up **compiles, uploads, runs, and silently does the wrong thing**. Both mirrors carry
the identical asymmetry, so it is real. `[MIRROR]` + `[LEGO]` example.

### 3.2 `steering`

Unitless int **−100…+100**. `0` = straight, **positive = right / clockwise**, negative = left. `±50`
stops one wheel (pivot turn); `±100` counter-rotates the wheels (spin in place).

LEGO's own API text states **only the range** and never names the directions — the direction mapping is
corroborated by SPIKE-3 community lessons, not by LEGO. It is also a ten-second floor check. Treat as
`[INFERRED]`, confirm on the bench.

> **Correction.** An earlier draft added *"`velocity` under steering applies to the FASTER wheel; the
> inner wheel is scaled down from it."* **Neither cited source says this.** It is plausible (it matches
> the EV3 convention) but it is `[UNVERIFIED]`, and it decides whether a steering turn preserves outer-
> wheel speed or average speed — which changes sweep leg timing. Marked `[ASSUMED]` until measured.

### 3.3 Open: is `motor_pair` actually synchronised?

LEGO says only *"run motors in a synchronized fashion … start and stop at the same time"*. Whether it
closes a cross-motor loop or merely issues simultaneous independent commands is **`[UNVERIFIED]`**, and
no source resolves it. This is the standing bench item: a 3 m open-loop straight run, both directions.
If it does not close a loop, heading hold is entirely ours to write.

### 3.4 Canonical skeleton

```python
from hub import port
import motor, motor_pair, runloop

async def main():
    motor_pair.pair(motor_pair.PAIR_1, port.C, port.D)   # (pair, LEFT, RIGHT)

    motor_pair.move(motor_pair.PAIR_1, 0, velocity=300)  # non-blocking, returns None
    await runloop.sleep_ms(2000)

    status = await motor_pair.move_for_degrees(          # blocking; yields a motor.* status
        motor_pair.PAIR_1, 720, 0,
        velocity=300, stop=motor.SMART_BRAKE)
    if status == motor.STALLED:
        pass

    motor_pair.stop(motor_pair.PAIR_1, stop=motor.BRAKE)

runloop.run(main())
```

## 4. `color_sensor` and `color` — the mission-critical pair

### 4.1 The surface, measured

```
dir(color_sensor) -> color  reflection  rgbi
dir(color)        -> BLACK MAGENTA PURPLE BLUE AZURE TURQUOISE GREEN YELLOW
                     ORANGE RED WHITE UNKNOWN
```
`[MEASURED]` — exactly three functions. No ambient, no LED control, no `wait_until_color`.

| Call | Units / range | Returns |
|---|---|---|
| `color_sensor.color(port)` | one of the `color` constants | int |
| `color_sensor.reflection(port)` | **0–100 %**, illuminated by the sensor's own **white** LED (not red like EV3), calibrated black=0 / white=100 `[LEGO]` | int |
| `color_sensor.rgbi(port)` | `(red, green, blue, intensity)` — ⚠ **LEGO documents NO range** | tuple[int × 4] |

`color` constant integers `[LEGO]` + `[MIRROR]`, **`[UNVERIFIED]` on our hub**: `BLACK=0 MAGENTA=1
PURPLE=2 BLUE=3 AZURE=4 TURQUOISE=5 GREEN=6 YELLOW=7 ORANGE=8 RED=9 WHITE=10 UNKNOWN=−1`. The module is
shared with the **output** devices (`color_matrix`, `hub.light`), which is why `PURPLE` and `TURQUOISE`
exist at all — do not expect the sensor to return 2 or 5.

**Use `==`, not `is`.** LEGO's own example writes `if color_sensor.color(port.A) is color.RED:`. That
happens to work because MicroPython represents small ints as tagged immediate values, but it is a
latent trap and we should not copy it.
> **Correction.** An earlier draft explained this as "CPython-style small-int interning". Wrong
> mechanism, right advice.

### 4.2 ⚠ The `rgbi()` range is not documented by anyone at LEGO

A grep of two saved copies of LEGO's own Python help page finds **zero occurrences of "1024"**. LEGO's
full text is only *"Retrieves the overall color intensity and intensity of red, green and blue."*

The nominal **0–1024** figure is real but comes from three non-LEGO places: the LPF2 device-mode table
for device 61 mode 5 "RGB I" (RAW 0–1024, 4 datasets); the jvolkening stub's author-added wording; and
LEGO's *Word Blocks* raw R/G/B blocks, which read the same sensor mode.

**So: 0–1024 is the nominal full scale; the achieved max on our floor, our sticky notes and our
mounting height is a different number and is `[UNVERIFIED]`.** This is a bench item, not a constant to
hard-code — and it is why the classifier below is written scale-free.

Also `[UNVERIFIED]`: what the 4th element, "intensity", is. LEGO says only "the overall color
intensity" — whether that is `(R+G+B)/3`, `R+G+B`, or a separate clear-channel photodiode is documented
nowhere. **Do not assume it equals a computed I.**

### 4.3 The mission question: will the built-in colour ID classify a sticky note?

LEGO's tech spec prints the sensor's hardware output set as eight LEGO **brick** colours plus "No
object", each with its reference RGB triplet `[LEGO]`: White (244,244,244), Blue (30,90,168), Black
(0,0,0), Green (0,133,43), **Yellow (250,200,10)**, Red (180,0,0), Medium azur (104,195,226), Bright
reddish violet (144,31,118). LEGO's *software* docs list **nine** recognisable colours, adding Orange —
which is absent from the hardware list, and which hands-on SPIKE 3 testing found unrecognisable.

> **Correction — this is the claim the verifier hit hardest, and it was overstated.** An earlier draft
> concluded that a pastel note "should be expected to return WHITE or UNKNOWN, not YELLOW", from a

classification.

### 4.4 Scale-free classification from `rgbi()`

Hue is illumination-invariant, so an HSI classifier does not need recalibrating as the battery sags.
Gate it, and **report UNKNOWN with a reason rather than forcing a class** — the reason code is required
by [color-discrimination.md](./color-discrimination.md).

```python
# PURE -- no LEGO import. Belongs in src/classify.py, never a hub_*.py.
import math

S_MIN, I_MIN, I_MAX = 0.10, 0.10, 0.90     # PLACEHOLDERS -- close them on the bench

def hsi(r, g, b, full_scale):
    """(hue_deg, sat 0..1, intensity 0..1) or ('UNKNOWN', reason). Scale-free:
    identical for 0-255, 0-100 or 0-1024 inputs -- which is why it is safe to
    write BEFORE rgbi()'s real range is known."""
    if full_scale <= 0:
        return ("UNKNOWN", "bad_scale")
    inten = (r + g + b) / 3.0
    if inten <= 0:
        return ("UNKNOWN", "black_clipped")
    sat = 1.0 - min(r, g, b) / inten
    denom = math.sqrt((r - g) * (r - g) + (r - b) * (g - b))
    if denom == 0:
        return ("UNKNOWN", "grey_no_hue")
    hue = math.degrees(math.acos(max(-1.0, min(1.0, (r - 0.5 * g - 0.5 * b) / denom))))
    if b > g:
        hue = 360.0 - hue
    i_frac = inten / full_scale
    if sat < S_MIN:
        return ("UNKNOWN", "low_saturation")
    if not (I_MIN <= i_frac <= I_MAX):
        return ("UNKNOWN", "out_of_range_intensity")
    return (hue, sat, i_frac)
```

⚠ **The gate contradicts the target and must be resolved before this ships.** `I_MAX = 0.90` exists to
reject blown-out readings — but pastel-on-a-light-floor is *exactly* where high intensity lives. If the
mission target sits above the gate, this classifier returns UNKNOWN on every mine it is meant to find.
Either the gate or the assumption is wrong; the bench decides which.

- **Spot size ~12–16 mm** at that height (one third-party rack-and-pinion measurement, 24 mm bar →

### 4.6 ⚠ Mode thrash — and a measured door that was thought closed

One sensor holds one LPF2 mode at a time. `color()`, `reflection()` and `rgbi()` are `[INFERRED]` to
select modes 0, 1 and 5 respectively — the mode *names and numbers* are sourced, but **no source states
that the Python functions select them, or that a switch happens per call rather than being cached.**
Nothing documents what a mode change costs in latency. Alternating two modes every loop iteration is
therefore an unbounded, unmeasured stall in the middle of the sweep.

**Pick one mode for the whole run, and pick `rgbi()`**: its intensity channel does the presence job
`reflection()` would do, and its R/G/B do the classification job `color()` cannot be trusted with.
This means [../../src/hub_color.py](../../src/hub_color.py)'s header comment ("detect on REFLECTED
LIGHT … `read_reflection()` is THE primary detection signal") disagrees with
[color-discrimination.md](./color-discrimination.md) § 1.2, and on the evidence the doc is right.
**That is a Programmer/operator decision to make explicitly, not a change to slip in.**

> **Correction, from our own hub.** Earlier research stated flatly that the LPF2 modes the hardware has
> but the API does not reach — AMBI (ambient), RREFL, HSV, SHSV — are **unreachable from stock SPIKE 3
> Python**, and that `device` has "NO mode setter". **Our measured `dir(device)` contains `set_mode`,

## 5. `runloop` and the asyncio model

### 5.1 The surface, measured — and it is NOT what LEGO documents

```
dir(runloop) -> run  sleep_ms  until  wait
constants    -> SUCCESS  CANCELLED  TIMEOUT  WAITING
```
`[MEASURED]`

> **Correction, from our own hub.** Earlier research stated *"exactly THREE public functions — `run`,
> `sleep_ms`, `until` — and nothing else"*, sourced to LEGO's documentation. **Our hub has a fourth,
> `wait`, and four status constants that LEGO does not document at all.** The research statement was
> true of the *documentation* and false of the *module*. `wait`'s signature is `[UNVERIFIED]`.

| Call | Units | Notes |
|---|---|---|
| `runloop.run(*functions)` | — | starts any number of coroutines in parallel; returns `None` |
| `runloop.sleep_ms(duration)` | **milliseconds** | returns an Awaitable — **must be awaited** |
| `runloop.until(function, timeout=0)` | `timeout` **ms**, `0` = no timeout | returns an Awaitable |
| `runloop.wait(…)` | `[UNVERIFIED]` | undocumented by LEGO; present on our hub |

### 5.2 ⚠ `until()` resolves on timeout too

LEGO, verbatim: *"If the callable does not return True within the timeout, the `until` still resolves
after the timeout."* LEGO documents **no return value** distinguishing the two exits. For a minesweeper
that is precisely the difference between "found a mine" and "my watchdog fired".

```python
# WRONG -- reports a mine every time the watchdog expires
await runloop.until(yellow_seen, timeout=2000)
report_mine()

# RIGHT -- the timeout is a watchdog; the predicate is the answer
await runloop.until(yellow_seen, timeout=2000)
if yellow_seen():
    report_mine()
```

**But our measured `runloop.TIMEOUT` / `SUCCESS` / `CANCELLED` / `WAITING` constants strongly suggest
`until()` (or `wait()`) does in fact return a status.** `[INFERRED]`, and worth one probe — if it does,
the re-check idiom above becomes belt-and-braces rather than the only defence. Until then, **re-check
the predicate.**

Also `[UNVERIFIED]` and mission-relevant: **how often `until()` polls its predicate.** At 150 mm/s a
10 ms poll is 1.5 mm of along-track position error; a 50 ms poll is 7.5 mm.

### 5.3 Cooperative scheduling — the rules

LEGO states them explicitly: *"Your coroutines should at least await one command. When you use a tight
while loop, use `await runloop.sleep_ms(1)` inside the loop to give other coroutines a chance to start
and run."* There is no pre-emption and no `_thread` module on this hub.

**Sensor reads are NOT awaitable and never yield.** `color_sensor.*`, `distance_sensor.distance`,
`force_sensor.force`, `motor.relative_position`, `motion_sensor.tilt_angles`, `device.data` all return
immediately. A detector loop that only reads sensors will starve every other coroutine unless you put
the yield in yourself.

The complete set of Awaitable-returning calls, from a `-> Awaitable` sweep of LEGO's reference, is
**19**: `motor.run_for_degrees / run_for_time / run_to_absolute_position / run_to_relative_position`,
`motor_pair.move_for_degrees / move_for_time / move_tank_for_degrees / move_tank_for_time`,
`hub.light_matrix.write`, `hub.sound.beep`, `runloop.sleep_ms`, `runloop.until`, and seven `app.*` calls
**that do not exist on our hub**.
> **Correction.** An earlier draft's list wrongly included `runloop.run` (returns `None`) and
> `app.display.*` (not awaitable), and mis-named the `app.bargraph` / `app.linegraph` getters.

### 5.4 Fire-and-forget vs await

LEGO: *"you can wait for it to complete, but you don't have to. By default, the program immediately
continues to the next line of code while the awaitable code runs to completion in the background."*
That is the shape our sweep leg should copy:

```python
motor_pair.move(motor_pair.PAIR_1, 0, velocity=500)              # start, do not await
await runloop.until(lambda: distance_sensor.distance(port.B) < 150)
motor_pair.stop(motor_pair.PAIR_1)
```

⚠ **`runloop.sleep_ms()` without `await` is a silent no-op** — it builds an Awaitable, never schedules
it, and delays nothing. **LEGO's own official Feb-2024 program collection ships this bug twice**,
including at the bottom of a `while True:` polling loop, which therefore spins flat out and never
yields. **You cannot trust delays in copied SPIKE 3 sample code**, and a bare-expression
`runloop.sleep_ms(...)` statement in `src/hub_*.py` is a bug worth a lint rule.

### 5.5 `asyncio`, `_asyncio`, `uasyncio` — three names, one implementation

Our measured module list matches upstream MicroPython v1.24.0's frozen `asyncio` manifest name-for-name
(`__init__ core event funcs lock stream`, and **no** `asyncio/task`, which the C module provides).
`_asyncio` is the C module (`TaskQueue`, `Task`); `uasyncio` is a six-line lazy-forwarding shim. There
is no second event loop and no LEGO fork of it. **Nothing of ours should ever import `uasyncio`.**

The scheduler's timebase is `time.ticks_ms` — **1 ms resolution**, so ~1000 Hz is the hard ceiling for
anything gated on a sleep or timeout, and `sleep_ms(0)` is a bare yield.

> **Two corrections.** (1) An earlier draft said our module list matches upstream *"byte-for-byte"* —
> `help('modules')` yields names, not bytes, and our own `os.uname().version` says
> `v1.20.0-1742.gf212bbe83`, i.e. a **LEGO fork** whose git-describe base is v1.20.0. Upstream v1.24.0
> source is a strong proxy, **not** proof; LEGO may have patched `extmod/asyncio`. (2) It inferred that
> `runloop` must be a firmware C module "because it appears as a bare name in `help('modules')`". That
> inference is invalid — `uasyncio` is a frozen *Python* module and also appears as a bare name.
> **Whether `runloop` is layered on `asyncio` at all is `[UNVERIFIED]`**, and the 1 ms floor is proven
> only for `asyncio`.

`asyncio/funcs` (`gather`, `wait_for`), `asyncio/event` and `asyncio/lock` are all on our hub
`[MEASURED]` — none of which `runloop` offers. Whether LEGO's awaitables interoperate with them is
`[UNVERIFIED]`. **Do not build on it**; a mission program must not depend on unsupported territory.

### 5.6 No published loop rate, anywhere

LEGO publishes no loop rate, no per-call latency and no sensor sample rate for any Python function; the
only qualitative statement in the corpus is that a 1 ms sleep *"is enough for the Hub to run many
coroutines concurrently"*. Real SPIKE 3 community control loops (e.g. a published PID line follower)
use a bare `while True:` with **no await and no delay at all** — which works only because they are the
sole coroutine, and means their tuned gains are bound to an unmeasured rate and will not transfer.
This leaves row 3 of [hub-compute-limits.md](./hub-compute-limits.md) § 3.1 exactly where it was: the
Python loop rate is the load-bearing unmeasured number.

### 6.1 ⚠ Yaw WRAPS at ±180° — it does not accumulate

**`[MEASURED]` 2026-08-27** (up from `[MIRROR]`): yaw min/max **−1795 / +1771 ddeg** across a hand rotation.

−1795…1800 decidegrees is a wrapped heading, not an unbounded integrator. LEGO's own turn idiom
sidesteps this by calling `reset_yaw(0)` immediately before **every** turn and keeping each turn under
180°. A 360° spin scan crossing the seam reads as a 3600-decidegree jump, which silently destroys any
angle-tagged sample.

> **Correction.** An earlier draft claimed this "breaks … the spin-scan in
> [spin-scan-localization.md](./spin-scan-localization.md)". It does not — that document already says
> *"Yaw wraps … the log must be unwrapped"* and already gates `reset_yaw(0)` on `stable()`. Nothing
> architectural changes.

```python
_prev, _turns = None, 0

def unwrapped_yaw_ddeg():
    """Continuous decidegrees. Call often enough that the true change is < 180 deg."""
    global _prev, _turns
    y = motion_sensor.tilt_angles()[0]
    if _prev is None:
        _prev = y
        return y
    d = y - _prev
    if d > 1800:
        _turns -= 1
    elif d < -1800:
        _turns += 1
    _prev = y
    return y + _turns * 3600
```

### 6.2 Yaw is NOT drift-corrected — and cannot be

The hub is a **6-axis IMU: three-axis accelerometer + three-axis gyroscope, no magnetometer** `[LEGO]`,
identified in teardown as an ST LSM6DS3TR on an STM32F413 — and our own `os.uname().machine` says
`SPIKE Prime with STM32F413`, so that teardown is of our hardware. Gravity fixes only the two axes
perpendicular to it; rotation *about* gravity is unobservable to an accelerometer. **Pitch and roll are
gravity-referenced and do not drift long-term; yaw is pure gyro integration and drifts.** `[INFERRED]`,
but hardware-constrained: no firmware can drift-correct yaw on a 6-axis IMU. The API shape corroborates
— `reset_yaw()` exists, `reset_pitch`/`reset_roll` do not.

The documented community failure mode is the gyro settling its bias **while the hub is being moved**,
after which yaw sticks at 0 or drifts forever, and the published remedy is to **power-cycle the hub**
(not a reset, not a re-flash). **The mitigation is free and we are not using it yet:** gate
`reset_yaw(0)` on `stable()`.

```python
def zero_heading(timeout_ms=3000):
    """Zero yaw only once the hub is genuinely still. True if it happened."""
    deadline = time.ticks_add(time.ticks_ms(), timeout_ms)
    while time.ticks_diff(deadline, time.ticks_ms()) > 0:      # ticks_diff, NOT '<'
        if motion_sensor.stable():
            motion_sensor.reset_yaw(0)
            return True
        time.sleep_ms(50)
    return False        # caller decides: FAULT, or run DEGRADED and say so
```
> **Correction.** An earlier draft wrote `deadline = time.ticks_ms() + timeout_ms` and compared with
> `<`. MicroPython `ticks_ms()` **wraps**, and its values are not valid for direct arithmetic or
> ordering — the documented API is `ticks_add` / `ticks_diff`. On a 60 s drift measurement a wrap
> silently ends the run early or hangs it.

Because [../findings/coverage-time-budget.md](../findings/coverage-time-budget.md) already puts a
feet-sized arena at 8–23 minutes, **uncorrected yaw drift is a first-order error term over a run that
long, not a rounding detail.** The drift **rate** is `[UNVERIFIED]` — no source gives a SPIKE 3 number,
and it is hub-, temperature- and settling-dependent. That measurement is a results-section number for
the Intro Report.

### 6.4 ⚠ LEGO's own docs contradict themselves about which face is which

In the same official document: the **constants block** says `TOP` is "the face with the Light Matrix",

waveform, channel)`** — frequency Hz, duration ms, volume 0–100. Our positional `sound.beep(freq_hz,
ms)` is correct; it inherits `volume=100`, which makes `sound.volume(0-100)` the only loudness control
at the demo. ⚠ The waveform integers conflict between the firmware dump (`SINE=0 TRIANGLE=1 SQUARE=2
SAWTOOTH=3`) and LEGO's docs (`SINE=1` **and** `TRIANGLE=1`, self-inconsistent) — **symbolic names
only**. `sound.play` is present `[MEASURED]` and undocumented for `hub.sound`; the sound-*file*
playback in LEGO's examples is the separate `app.sound`, **which does not exist on our hub.**

⚠ **`beep()` and `write()` return Awaitables.** Called without `await` they start and return
immediately. LEGO's Hello-World runs `light_matrix.write(...)` unawaited and it does scroll, so
fire-and-forget is real, not a no-op. Whether two back-to-back unawaited `beep()`s **queue, overlap or
truncate** is `[UNVERIFIED]` — which is exactly the risk `hub_ui.py:tone_rising()/tone_falling()` carry:
they may or may not be distinguishable across a classroom, which is the whole point of having two.
> **Correction.** An earlier draft asserted as fact that they "will overlap into one indistinguishable
> noise" while its own unknowns list said the behaviour was untested. It is a risk, not a result.

**`light.color(light.POWER, color.RED)`** sets the two button LEDs from the `color` module — two free
status channels visible across the room that do not compete with the 5×5 for space. A three-argument
RGB form (`light.color(light.CONNECT, 90, 40, 2)`) appears in one mirror only and is `[UNVERIFIED]`.

## 9. `device` — the raw LPF2 layer

```
dir(device) -> id  data  ready  set_mode  reset_mode  write_mode
               get_duty_cycle  set_duty_cycle
```
`[MEASURED]`

`device.id(port)` is how we detect what is plugged into A–F at run start, which
[../plans/mission-algorithm.md](../plans/mission-algorithm.md) needs for its self-check. Device type
IDs `[LEGO]` + community registry: **48** Medium Motor 45603 · **49** Large Motor 45602 · **61**
Colour Sensor 45605 · **62** Distance Sensor 45604 · **63** Force Sensor 45606 · **65** Small Motor
45607 · 75/76 retail Powered UP motors.

```python
def color_sensor_present(p):
    """True only if a 45605 is on port p AND has finished enumerating."""
    try:
        return device.ready(p) and device.id(p) == 61
    except Exception:
        return False
```

> ⚠ **`set_mode`, `reset_mode` and `write_mode` are WRITES to the attached device** — not read-only, so
> they **must not go into `probes/`** ([probe-with-scripts-not-commands.md](../lessons_learned/probe-with-scripts-not-commands.md)).
> Their presence overturns the earlier claim that `device` has no mode setter and that the LPF2 modes
> the Python API does not expose are therefore unreachable — see [§ 4.6](#46--mode-thrash--and-a-measured-door-that-was-thought-closed).
> Exploring them is a Builder/operator bench decision on a sensor we do not yet own.

## 9b. `orientation`, and the rest

```
dir(orientation)     -> UP RIGHT DOWN LEFT           (0, 1, 2, 3 -- values [MIRROR])
dir(color_matrix)    -> clear get_pixel set_pixel show
dir(distance_sensor) -> distance  clear get_pixel set_pixel show
dir(force_sensor)    -> force pressed raw
```
`[MEASURED]`

`orientation` exists **only** to feed `light_matrix.set_orientation()`. Do not confuse `orientation.UP`
(a display rotation) with `motion_sensor.TOP` (a physical hub face) — different modules, different
value spaces, and both appear in code that touches the display.

`distance_sensor.distance(port)` returns **millimetres, and −1 when there is no valid reading** — one
of the few places the LEGO API uses a sentinel rather than an exception. Our own convention is `None`,
never `0`; the `hub_*.py` wrapper is where −1 becomes `None`. Its `set_pixel`-style calls address the
sensor's own LED eyes, not a rangefinder feature.
