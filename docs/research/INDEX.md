| [spin-scan-localization.md](./spin-scan-localization.md) | **Can we make a scanning rangefinder by spinning the robot?** The operator's spin-SLAM proposal, assessed on the evidence: the *mechanism* works and is free (the robot already spins; the 250 mm sensor lead rotates with the hub, so nothing winds), but the 45604 is **ultrasonic** with a **±35° entrance angle** — a ~70° cone giving ~5 independent bearing cells per revolution, no point cloud, and a hard 2000 mm ceiling. Corrects the accelerometer/gyro confusion (yaw comes from the gyro; the accelerometer's job is proving the robot is flat, and gyro-vs-encoder *disagreement* is a free slip meter). Localizing in a known rectangle needs no SLAM — 5 scalars, no matrices, fits the hub easily. **Keeps** forward range reads during a lane and **one** run-start scan — as an exteroceptive *cross-check* on the arena size and a pose fix, not a way of discovering an unknown arena, because the ±476 mm centre window it needs cannot be reached without already knowing the size (SS-7); **rejects** per-lane spin re-squaring (~±3.5° vs the wall bump's 0.6°, for 1.9–3.2 min of run time). | [ble-bring-up.md](./ble-bring-up.md) | **Why the hub shows no light on its Bluetooth button and advertises nothing — and what to do about it.** Opens with the DFU hazard: **holding the CONNECT button while USB is plugged in is the documented bootloader gesture**, and its pink-green-blue-off cycle shares all three colours with LEGO's "Hub OS updated, restart me" pattern. Then the ranked answer: the leading explanation is that **LEGO's Hub OS was not running**, because every probe in this repo fires `Ctrl-C` twice before it speaks — `[INFERRED]`, resting on one confirmed plank (the hub exposes **one** CDC-ACM function, `0694:0009` "SPIKE Prime VCP", and LEGO's COBS protocol owns that same port, so a `>>>` on it means the Hub OS is not driving it) plus two extrapolations a verifier struck down. Eight hypotheses, each with the test that discriminates it, labelled **read-only / low / medium / high**, DO-NOT-RUN list at the **top**, and the decisive first test costing nothing: **look at the hub** — LEGO documents the centre button as solid green for any healthy powered hub and documents **no dark state**. Identification: LEGO documents exactly one advertising fact (the FD02 service UUID is in the payload), our `device_uuid` is the **STM32 die ID** and physically cannot be advertised, so matching is filter-FD02 → connect → `DeviceUuidRequest 0x1A` → compare 16 bytes; **the BLE address type is UNKNOWN and every "it's a stable MAC" source turned out to be Bluetooth Classic / Hub OS 2 tooling** — struck, though a rotating address costs us only the fast path, not correctness. Concrete `bleak` connect-and-upload with the framing bytes **computed from LEGO's own `cobs.py` on this host** (`InfoRequest` = `00 00 02`, and the earlier hand-typed `02 03 02` was wrong **and contained a raw `0x03` = Ctrl-C**), the chunk-size-must-be-a-multiple-of-4 CRC proof, the reassembly LEGO's own example admits it lacks, and a required **allowlist** so no tool can ever emit firmware message ids 10/20. **Our earlier "a hub program cannot drive its own radio" inference is dead** — `dir(bluetooth.BLE)` is the full GAP+GATT surface — but the verdict is unchanged and now argued on mechanism: a single un-chainable `irq` slot, `gatts_register_services` that resets the GATT DB, a shared singleton, and zero latency or throughput gain over `hub.config['module_tunnel']`, which is already binary and bidirectional. **Don't pursue it before 10 SEP.** § 7 is a corrections register naming every claim a verifier overturned |
| [bluetooth-control-plane.md](./bluetooth-control-plane.md) | **Can we upload and manage code over Bluetooth instead of USB, and stream telemetry off an untethered robot?** LEGO's own BLE protocol reference read at source: GATT service `0000FD02-…` with hub-RX/hub-TX characteristics, write-without-response + notifications, the COBS-with-escapes/XOR-0x03/delimiter framing and standard zlib CRC32, and the complete message id table. **Upload to a slot and start/stop it do work over BLE** — but the real find is **`DeviceNotification` (id 60)**, which streams battery, IMU yaw/pitch/roll + raw accel + raw gyro, every motor's position/speed/power, the colour sensor's **raw R/G/B 0–1023** and distance in mm to the laptop at a requested interval **with no hub-side code at all** — the untethered telemetry the parked [telemetry plan](../plans/telemetry-and-analysis.md) wanted, on a robot with no cable dragging its heading. **Hub OS 3 only** (Hub OS 2 is Bluetooth Classic RFCOMM + JSON-RPC — a different stack), so it is gated on KU-M1, and a BLE scan is itself the generation test. Throughput is governed by LEGO's **stop-and-wait** chunk loop, not by MTU or framing: chunks × RTT, and the RTT is **UNMEASURED** — this host's kernel *prefers* a 30–50 ms connection interval, but no link has ever existed and the hub negotiates its own. No slot listing, no file download, no REPL over BLE — those stay USB. No released version of the VS Code extension implements either telemetry message (an **open, unmerged PR #80** would), and its BLE console readback is broken by another **open, unmerged PR #81**. **Verdict: supplement, don't replace** — dev loop stays USB, add one read-only `bleak` telemetry script, and never let a run depend on the link. Carries a four-phase go/no-go bench procedure that closes KU-M1 without a cable and never risks a Hub OS update prompt. **Nothing tested — no hardware exists** |

**Watch the API generation.** Most SPIKE tutorials online target the legacy SPIKE 2 API
(`from spike import PrimeHub`). The current API is `import motor` / `from hub import port` /
`import runloop`. Check which one a source targets before believing it.
